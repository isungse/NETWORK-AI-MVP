# 장애 감시 운영 안내

## 화면과 데이터 범위

`/`, `/operations`, `/monitoring`은 동일한 한국어 장애 감시 화면을 제공한다. 첫 화면은 여섯 지표와 건물 → 층 → 장비별 스위치 패널로 구성한다. 장애 장비와 층을 먼저 표시하며, 정상 장비를 포함한 전체 물리 포트 패널을 기본으로 펼친다. 층 선택으로 표시 범위를 좁힐 수 있다. 포트 번호·상태등·상태명과 업링크 `↑`, 중요 포트 `★` 표시로 상태를 구분한다. 논리 번호 배열은 실제 전면 배치 확정을 의미하지 않는다. 포트를 선택하면 해당 포트 상세를 열며, MAC, 승인 기반 차단·복구, 장애·복구 이력은 상세에 유지한다.

이전 대시보드의 저속·누적 오류 통계, 전체 토폴로지, 원시 CLI, 검색·진단 실행 버튼은 새 화면에서 제외했다. 기존 수집, 관측 이력, CLI 정책, 조회 API 및 승인 감사 기록은 유지한다. 이전 정적 자산은 호환성과 기존 작업 보존을 위해 남겨 두었으나 새 사용자 경로에서는 로드하지 않는다.

## 슬롯 제목 별칭

모든 등록 장비의 슬롯·포트 그룹은 패널과 장비 상세 배치도에서 제목 옆 `편집` 버튼으로 별칭을 설정한다. 섀시·스택은 확인된 슬롯별로 저장하고, 슬롯 구분이 없는 고정형 스위치는 기본 포트 그룹에 저장한다. 같은 슬롯의 Gi/Te 그룹은 별칭을 공유한다. Arista TX3/SX3의 49~56번 `/1` 인터페이스는 슬롯으로 분리하지 않는다. 기본 슬롯 번호와 모델명은 유지하며 `슬롯 1 · WS-X45-SUP7-E (서버룸 BACKBONE 슬롯2)`처럼 표시한다. 별칭은 최대 80자이고 저장 전 미리보기를 제공한다. `취소`는 저장하지 않으며 `별칭 지우기` 후 `저장`하면 기본 제목으로 복원한다. 별칭은 표시용이며 실제 모델, 슬롯·포트 식별자, 장비 설정 및 감시 위치 설정을 변경하지 않는다.

별칭과 변경 전후 값·변경 시각은 로컬 `data/monitoring.sqlite3`의 `slot_aliases`, `slot_alias_audit`에 저장해 같은 서버를 사용하는 직원들과 공유하고 재시작 후에도 유지한다. 다른 화면에는 다음 화면 갱신 때 반영한다. 다른 직원이 먼저 수정한 경우 덮어쓰지 않고 최신 제목에서 다시 편집하도록 안내한다. 현재 내부 운영 화면 접근자에게 제공하는 메타데이터 편집이며 개인별 신원 인증·권한 기능은 아직 없다. 참고 배포에서는 편집 버튼을 제공하지 않고 직접 저장 요청도 거부한다.

## 최근 연결 포트와 이력

`NEW`는 실제 케이블 연결이 확인된 물리 포트에만 빨간 글씨와 청록색 테두리로 표시한다. 표시 기간은 확인 버튼을 누른 시각이 아니라 해당 연결 시각부터 24시간이다. 이후 링크 해제·복구, 재수집·재시작 또는 같은 기록의 재확인은 만료 시각을 연장하지 않는다. 연결 횟수는 확인된 물리 연결만 집계하며 반복 횟수와 관계없이 포트 표시는 `NEW`를 유지한다. 최초 연결 상태, 링크 Up 로그, Down→Up 및 미연결 관측 지속 시간만으로 실제 케이블 삽입을 확정하지 않는다. 이전의 10분 미연결 추정도 `NEW` 근거로 사용하지 않는다.

실제 케이블을 새로 연결한 사실을 확인한 운영자는 포트의 연결·해제 이력에서 해당 연결 기록의 `실제 케이블 연결 확인`을 선택한다. 잘못 확인한 경우 `물리 연결 확인 취소`로 되돌릴 수 있다. 입력은 해당 장비·물리 포트의 연결 기록에 한정하며 연결 해제, 논리 인터페이스, 시각 보정 근거가 없는 로그 및 미래 시각은 확인할 수 없다. 확인과 취소는 읽기 전용 수집이나 장비 설정 명령을 실행하지 않는 운영 메타데이터 변경이다. 별도 SQLite 확인 기록과 변경 이력을 저장하며 장비 로그와 관측 이력은 보존한다. 운영자 개인의 신원 인증 기능은 아직 없다.

상단의 최근 물리 연결 목록은 전체 장비 또는 선택한 층의 확인된 기록을 최신순으로 보여 준다. 포트 상세에서는 확인된 기록과 `링크 연결·복구 · 물리 연결 미확인`을 구분한다. 스위치 링크 상태만으로 실제 케이블 삽입과 이미 연결된 단말의 전원 켜짐을 완전히 구별할 수 없으므로, 현재 수집 근거만으로 물리 연결을 자동 확정하지 않는다. MAC·IP는 별도로 수집된 단말 근거이며 연결자 신원에는 자산·사용자 인증 정보가 필요하다.

자동 감시는 `interfaces` 수집 성공 뒤 읽기 전용 `connection-events` 목적(`terminal length 0`, `show clock`, `show logging`)을 수집한다. Cisco LINK 및 장비 시계로 연도를 확인할 수 있는 Arista LINEPROTO 로그를 사용하며, 유효한 연속 상태 수집의 변화도 이전·현재 수집 사이의 시간 범위로 기록한다. 장비 시계 차이를 보정한 시각과 원래 장비 시각을 함께 보존하되 수집 지연 오차가 있다. 해석할 수 없는 날짜·시간대는 추정하지 않는다. 같은 이벤트의 상태 변화와 로그는 통합하고 재수집 로그는 중복 기록하지 않는다. 확인된 관측이 뒤늦게 로그와 통합되어도 기존 물리 연결 확인과 만료 시각은 보존한다. 수집 실패·오래된 관측 뒤 첫 정상 상태로 연결 시각을 추정하지 않는다. 로그 수집 실패는 정상 포트 수집을 무효화하지 않는다. 로그 버퍼 유실, 미지원 형식 및 수집 사이의 짧은 연결은 누락될 수 있다.

이벤트, 물리 연결 확인과 변경 이력은 기존 `data/monitoring.sqlite3`에 저장해 재시작 후에도 유지한다. 기록은 30일 보관하고 상세는 최근 100건을 제공한다. 참고 배포에서는 `NEW`를 표시하지 않으며 물리 연결 확인·취소 요청도 거부한다.

## 명시적 감시 설정

설정 원본은 [`inventory/monitoring.json`](../../inventory/monitoring.json)이다. 설정 수정 후 로컬 서버를 재시작한다. 시작 시 형식과 확인 주기를 검증하며 잘못된 설정으로 감시를 시작하지 않는다.

- `building`, `floor`, `location_source`: 확인된 건물·물리적 설치 층과 출처. 호스트명이나 IP로 추정하지 않는다. `null`은 미확정이다.
- `uplinks`: 지정 업링크 목록. `null`은 미설정, `[]`는 관리자가 명시적으로 대상 없음으로 확정한 경우에만 사용한다.
- `important_ports`: 업무상 감시할 포트 목록. 미사용 포트는 등록하지 않는다. `null`은 목록 미확정이고 `[]`는 중요 포트 없음으로 확정한 상태다.
- 각 포트는 `interface`, `source`, `impact`를 기록한다. `impact`에는 실제 확인된 업무·단말·하위 범위만 적는다. 기본 `expected`는 `up`이며, 중요 포트에 한해 `disabled`를 명시하면 계획된 비활성 상태로 구분한다.

초기 설정은 저장소에 명시된 층과 LLDP/CDP 연결 근거만 반영한다. 건물명, 중요 포트 목록은 확보되지 않아 미설정으로 시작한다. 외래 스위치처럼 호스트명의 층과 서비스 층이 혼재하는 위치는 임의 확정하지 않는다. 업링크 출처는 참고 연결 근거이며 실시간 정상 상태를 의미하지 않는다.

## 수집 및 판정

로컬 서버의 `NETWORK_AI_POLLING=1` 설정으로 주기 수집을 켠다. Vercel에서는 수집기를 시작하지 않으며 참고 스냅샷만으로 현재 정상을 표시하지 않는다. 브라우저를 닫아도 로컬 수집은 계속되고 서버를 종료하면 중단된다. 자동 시작을 위한 Windows 서비스 등록은 별도 운영 작업이다.

기본 설정은 전체 수집 완료 후 120초 대기, 동시 수집 3대, 장비별 제한 30초, 데이터 유효 기간 600초, 장애 확정 3회, 복구 확인 2회다. 모두 설정 파일에서 변경할 수 있다. 장애/복구 연속 횟수는 새로운 실제 수집 결과로만 진행하고, 최소 10초 간격을 둔다. 화면은 15초 간격으로 새 상태를 읽는다. 실제 장비별 주기는 전체 수집 소요 시간에 따라 120초보다 길어진다.

| 상황 | 판정 |
| --- | --- |
| 지정 업링크가 연속으로 연결 끊김 또는 관리상 비활성 | 업링크 장애 |
| 지정 중요 포트가 연속으로 기대 상태와 다름 | 중요 포트 장애; 물리 링크 끊김과 관리상 비활성을 구분 |
| 미사용·미지정 포트 Down 또는 10/100Mbps 연결 | 중대 장애 집계 제외 |
| 수집 실패와 별도 관리 TCP 응답 없음이 연속 확인됨 | 장비 통신 불가·원인 확인 필요 |
| 인증·권한·파싱 실패, 관리 포트 연결 거부 또는 원인 불명 | 상태 확인 불가; 전원 장애로 추정하지 않음 |
| 수집 시각이 유효 기간을 초과하거나 미수집 | 상태 확인 불가; 상세 배치도도 현재 정상 색상 표시 금지 |
| 확정 장애 뒤 연속 정상 수집 | 복구 시각 기록; 확인 중에는 정상으로 표시하지 않음 |
| 설정 누락 또는 지정 포트가 수집 결과에 없음 | 상태 확인 불가 |

장비 전체 통신 불가 시 확인하지 못한 모든 업링크·중요 포트를 개별 장애로 중복 집계하지 않는다. `중대 장애 장비 수`는 중복 없는 장비 수, 업링크·중요 포트 수는 확정된 포트별 건수다. 설정 누락과 장애가 동시에 있는 장비는 중대 장애와 확인 불가 두 지표에 모두 포함될 수 있다.

현재 전원 센서·UPS·PDU 데이터가 없으므로 전원 장애 판정은 지원하지 않는다. 최초 감지는 관측 시작 시각으로 실제 장애 시작 시각과 다를 수 있다. 과거 스냅샷 하나를 연속 관측 여러 번으로 간주하지 않는다.

## 상태 보관과 변경 보호

최근 수집 상태, 연속 확인 횟수, 최초 감지·확정·복구 시각은 로컬 `data/monitoring.sqlite3`에 저장한다. 기존 `data/raw`, `data/observations`, 수집·변경 감사 로그는 그대로 유지한다. 데이터와 자격증명은 Git에 넣지 않는다. 현 수집기는 단일 서버 프로세스용이며 다중 worker 실행은 지원하지 않는다.

지정 업링크, 백본 역할 장비, 문서에 있는 백본 연결, 과거 관측에서 이웃·업링크가 확인된 포트는 서버에서도 변경을 거부한다. 업링크 목록 자체가 미설정인 장비도 변경 대상에서 제외한다. 이웃 기록에는 PC가 포함될 수 있으므로 보수적으로 보호하며, 이를 없애서 차단을 우회하지 않는다. 기존 승인 코드·만료되는 명령 미리보기·실시간 전후 확인·감사 기록·복구 명령은 유지한다. 주기 수집과 동기 포트 변경은 동일 장비 잠금으로 직렬화한다.

새 흐름에서 승인·검증된 중요 포트 차단은 계획된 비활성 예외로 저장하고 장애 복구로 위장하지 않는다. 이력에는 `관리자 승인 차단`을 기록한다. 외부에서 차단했거나 과거 승인 기록만 있는 경우 의도를 자동 추정하지 않고 `관리상 비활성`으로 구분하므로 관리자가 감시 설정을 확인해야 한다.

## 재현 검증

```powershell
$env:PYTHONPATH='src'
python -m unittest discover -s tests
node --check src/network_ai_mvp/static/fault-dashboard.js
node --check src/network_ai_mvp/static/fault-panel.js
node tests/fault_panel.test.cjs
node --check src/network_ai_mvp/static/app.js
node --check src/network_ai_mvp/static/monitoring.js
node tests/switch_panel.test.cjs
git diff --check
```

`tests/test_fault_monitor.py`는 임시 데이터와 고정 시각으로 전체 정상, 업링크 장애, 통신 불가, 중요 포트 장애, 미사용 Down, 데이터 지연, 복구를 재현한다. 추가로 재시작 후 이력 유지, 인증 실패, 불완전 수집, 조회로 인한 중복 확정 방지, 의도된 차단, 참고 배포의 정상 판정 금지, 지정 업링크 보호를 검증한다. 실제 장비의 장애를 만들거나 포트를 차단하는 테스트는 실행하지 않는다.
